# OCA-201-SLICE -- which OCPP 2.0.1 certification cases this suite may
# implement, and which scenario implements each.
#
# THIS FILE IS THE LIST. OCA-201-SELECTION.md states the RULE it is drawn from
# -- role CSMS, status M in Part 5 §4's `Conf. test for CSMS` column, on every
# certification profile -- and cites this file rather than restating it. The
# same arrangement OCA-COVERAGE.md has with OCA-OBLIGATIONS.txt, for the same
# reason: two copies of a list drift, and the prose copy is the one nobody
# diffs.
#
# THE RULE SELECTS 147 CASES AND THIS FILE HOLDS 147. It stopped being a
# bounding list and became the pool when the matrix was re-parsed to keep the
# case identifier per row rather than only the per-profile count -- Part 5
# Edition 4, 2025-12-03, by the method on that page. Note what the same run
# corrected: the totals it replaced summed to 205, because on three of the four
# profiles a row had been counted as selected when `M` appeared in EITHER
# status column rather than in the CSMS one -- the reading that reproduces two
# of those three profiles' old numbers exactly, and the third to within one
# row. Whether a list this long may be committed at all was the other half of
# the gap, and it is settled: it may. CC BY-ND limits modification, not extent,
# and a list of case identifiers modifies nothing -- the argument, and the one
# risk it accepts, are in that page's "What may be committed here, and what may
# not".
#
# 147 CASES, 165 ROWS OF THE MATRIX. A case can be listed under two profiles,
# and a case is a case, so it gets one row -- which is also all this file can
# hold, since the guard refuses a second row for a case already listed. Which
# cases those are, and why the two numbers differ by 18 rather than by 37, is
# on that page with the rest of the derivation.
#
# Hand-maintained, and guarded: tests/oca-201-slice.sh reads it against
# tck/specs/ASSERT-INVENTORY.txt in both directions, so a `cert201-` scenario
# for a case that is not listed here and a case here that is neither
# implemented nor declined are both build failures.
#
# WHAT NO GUARD CAN CHECK: that these rows ARE mandatory CSMS cases the rule
# selects, and that they are ALL of them. That is a reading of a PDF this
# repository does not contain -- a reference is cited by URL and not committed,
# and OCA-201-SELECTION.md's licensing section says why that is our rule rather
# than the licence's -- and the method for redoing the reading is written down
# on that same page, now with the edition it was last run against. Note the
# second half: the guard ranges over this file, so a file short of the pool is
# a file it finds complete, and that this file is no longer short is a claim
# only a re-run of the parse can check. What is checked is that the list and
# the scenarios stop drifting afterwards.
#
# NOTHING OF THE REFERENCE'S OWN WORDS IS HERE, which is what leaves a row on
# the identifiers-and-counts side of the line that page draws. A reason below
# says what THIS suite lacks; none of them says what a case asks for.
#
# A row is three fields, the third free text:
#
#   <OCA case>  <templateId | not-implemented>  <why not, on a not-implemented
#                                                row; omitted on an implemented
#                                                one, where the scenario says it>
#
# A REASON IS WRITTEN PER GROUP, NOT PER CASE, and the repetition below is that
# rather than a placeholder. Twenty-six reasons cover the 121 declined rows,
# because that is the granularity the decision was actually taken at: a block's
# cases are blocked by one missing thing -- an operation the
# `CsmsOperation201` union does not have, a station-side message the pinned
# image cannot spell, a transport seam that does not exist. Splitting one
# reason into ten copies with the case id changed would read as ten decisions
# and be one. If a case is blocked by something its neighbours are not, it gets
# its own row text; five do -- TC_A_12, TC_B_58, TC_G_20, TC_K_15 and TC_K_31 --
# and TC_C_37 and TC_C_38 share a sixth, which is the same shape one size up.
# TC_K_10 used to have one for the other reason a row can be alone -- the
# blocker was its neighbours', the profile that makes it mandatory was not --
# and it is implemented now, which is what that shape usually turns into.
#
# AND WHAT THE SMART CHARGING TRANCHE DID TO THE K BLOCK, which is the third
# correction this file has recorded and the cheapest to have missed. Every K row
# declined on "charging profile operations are CSMS-initiated and none is among
# `CsmsOperation201`'s members", and two of them now are. Nine rows became
# implemented; the eleven still blocked by a charging-profile verb say WHICH
# verb -- ClearChargingProfile, GetChargingProfiles, RequestStartTransaction --
# because a sentence claiming the whole class is missing is now false about the
# class and true about the row, which is the reading that stops the next author
# looking. Two of the fifteen the tranche unblocked stayed declined for reasons
# that are theirs alone and are written on their rows: TC_K_15 wants an
# RPC-level answer the pinned simulator cannot produce, TC_K_31 a continued
# report it cannot mark. Shipping TC_K_31 on the request half alone would
# measure a spelling, which is what tests/get-configuration-filter.ts exists
# to record about the protocol next door.
#
# AND WHAT MEASURING THE CASES DID TO THOSE REASONS, because it is the cost of
# writing them per group before anything read Part 6. They were drawn from Part
# 5's arrangement, which groups by profile and functional block, and a block's
# cases do not all need the same thing: TC_M_24, TC_M_26 and TC_M_28 shared a
# reason with rows that really do need a certificate operation and turn out to
# need none -- they are the station asking the CSMS. TC_F_27's named a missing
# operation that is no longer missing. Both are corrected above, and
# tck/specs/OCA-201-OPERATIONS.txt is now what a reason naming an operation is
# checked against, which is the guard that would have found them.
#
# AND WHAT WRITING THE SCENARIOS DID TO THEM, a second time and from the other
# end. The C, E and J blocks all declined on "the pinned image ships no
# `cert201-` template, so nothing here drives that side", and the premise was
# false: a template is one way to drive the station and the simulator's
# JSON-Lines CLI is another, which is how TC_C_02, TC_E_10 and TC_J_01 came out
# of those three blocks -- one `authorize`, one `start_transaction`, one
# `send_meter_value`. The rewritten reasons name what actually remains, and it
# is a different thing per block: a stored authorization state no scenario can
# ask a driver for, a TransactionEvent member the image hardcodes, a
# `sampledValue.context` it drops. A reason that generalises from the tool that
# was reached for first is the same mistake the paragraph above records, made
# about a mechanism instead of about an operation.
#
# WHICH RESET OUTCOME IS WHICH CASE IS OUR READING, not something read off Part
# 6. `ResetStatusEnumType` has three values and the Reset block has three
# mandatory CSMS cases, so they are mapped Accepted / Scheduled / Rejected in
# case order. tck/specs/core-201.ts's header carries the argument. Correcting
# it moves three rows here and three templateIds there.
#
