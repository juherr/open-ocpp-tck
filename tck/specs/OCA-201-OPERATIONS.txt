# OCA-201-OPERATIONS -- which CSMS-initiated operation each selected OCPP 2.0.1
# certification case obliges the CSMS to send.
#
# THE QUESTION THIS ANSWERS IS NOT THE ONE OCA-201-SLICE.txt ANSWERS. That file
# says WHICH cases the rule selects and which scenario implements each; this one
# says HOW WIDE A VOCABULARY they ask for between them, which is what decides
# how far `CsmsOperation201` in tck/driver.ts has to grow and in what order. The
# two range over the same 147 cases and are checked against each other in both
# directions; they are separate files because they answer to separate
# references -- the slice to Part 5's matrix, this to Part 6's cases -- and a
# column bolted onto the slice would make one row answer to two.
#
# HOW MANY KINDS OF OPERATION THAT IS, AND HOW FAR SHORT OF IT THE UNION
# STANDS, ARE NOT WRITTEN HERE. The rows are, and tests/oca-201-operations.sh
# prints both counts off them on every run; OCA-201-SELECTION.md is where they
# are stated in prose, once, with the tranche table that spends them. Three
# copies of a derived number is how one of them ends up wrong, and this file is
# the one that would be believed.
#
# WHAT IS WORTH SAYING HERE is what a `none` row means, because it is most of
# them: a case that only observes charge-point-initiated traffic needs no verb
# at all, which is why "add the rest of the 2.0.1 messages" was the wrong shape
# for this. Those rows are blocked by other things -- a station-side event, a
# transport seam, certificate material -- and OCA-201-SLICE.txt's reason column
# is where that is said.
#
# MEASURED, THEN WRITTEN DOWN, the status OCA-COVERAGE.md's totals carry.
# `bun tools/extract-201-operations.ts <part6.pdf>` produces these rows; Part 6
# - Test Cases, Edition 4, 2025-12-03, the SAME edition OCA-201-SELECTION.md's
# per-profile counts were measured against. Two editions apart would make the
# two measurements incomparable while both kept reading well, so the edition is
# on both pages. `--diff` re-runs the parse against this file.
#
# WHAT NO GUARD HERE CAN CHECK is that a row is the reference's answer, for
# OCA-201-SLICE.txt's reason: the PDF is not in this repository and will not be.
# What is checked is that the rows, the slice and the driver's union stop
# drifting -- tests/oca-201-operations.sh, whose header states the three
# directions.
#
# WHY IT IS NOT DERIVED FROM THE SLICE'S REASONS. Twenty-two of those name an
# operation -- ChangeAvailability, UpdateFirmware, TriggerMessage -- and they
# were written from Part 5's groupings, per group and without aiming at
# exhaustiveness. Measured against Part 6 they are right where they are
# specific and wrong where they generalise: TC_M_24, TC_M_26 and TC_M_28 shared
# a reason with rows that do need a certificate operation, and drive none.
# The reasons are a cross-check on this file, which the guard runs; they are not
# its source.
#
# NOTHING OF THE REFERENCE'S OWN WORDS IS HERE. A row is a case identifier and
# an OCPP message name, and a message name is the protocol's vocabulary rather
# than the OCA's expression -- the same side of the line OCA-201-SELECTION.md's
# "What may be committed here, and what may not" already puts identifiers and
# counts on. This file says TC_G_03 needs ChangeAvailability; it never says what
# TC_G_03 asks anyone to do.
#
# A row is two fields:
#
#   <OCA case>  <operation[,operation] | none>
#
# `none` is measured, not missing, and the guard refuses an empty second field
# for that reason: the two must not render the same. Operations are sorted
# within a row so a re-run diffs clean.
#
# SIX CASES NEED TWO OPERATIONS, and they are why "cases needing X" and "cases
# X unblocks" are different numbers: TC_A_11, TC_A_12 and TC_A_14 need
# CertificateSigned AND TriggerMessage, TC_K_05 needs ClearChargingProfile AND
# GetChargingProfiles, TC_M_20 and TC_M_21 need DeleteCertificate AND
# GetInstalledCertificateIds. A tranche sized by the first number promises
# cases it does not deliver; OCA-201-SELECTION.md's tranche table counts the
# second.
#
# WHERE THE READING IS OURS. Part 6 attributes a request to the CSMS in three
# places -- a `Tool validations` line, a step of the scenario, and a Reusable
# State the case executes -- and this file unions all three, transitively
# through the states. The one that looks skippable and is not: TC_G_03's entire
# scenario is "Execute Reusable State Unavailable" with no tool validation at
# all, and ChangeAvailability is named only in that state. The extractor's
# header states the rest, including the two normalisations it applies.
#
